\section{Design}


%% Introduce AEBench overall workflow and a few key design points

\aebench is a framework for running and evaluating AI coding agents on artifact evaluation tasks. 
The main feature of \aebench is running the agents and recording runtime information
  to allow to validate whether or not the artifact actually ran the artifact and 
  didn't fake the results by copying them from the paper or artifact repository 
  through repository history.
  
\aebench runs an agent in a controlled environment, allows it to attempt the documented 
  reproduction procedure documented in the README file of the artifact, evaluates the result 
  using artifact specific checks which we called oracles, and checks the commands that 
  the agent runs against the README.

We design \aebench to implement both the execution framework and the evaluation framework
  but the two are separated and agents cannot see the evaluation stage.

\begin{itemize}
  \item \aebench execution framework prepares the artifact, launches an AI agent, manages its environment, and records what happens.
  \item \aebench evaluation framework independently checks whether the agent successfully reproduced the artifact's expected behavior or results.
\end{itemize}

\subsection{Agent Reproduction Task}

Artifacts are heterogeneous.
Some require complex installation,
  others a multi-step build and installation system,
  others still require to setup and run complicated 
  experiments that run for hours or even days.
Therefore a generic correctness check to indicate whether 
  the agent has successfully ran and reproduced the artifact 
  is impractical.

To solve this problem, \aebench uses a shared 
  four stage evaluation framework with 
  checks derived from the artifacts themselves.
More importantly, these checks are exercised once 
  the agent terminates so that the reproduction 
  workflow and the conditions determining whether 
  or not the agent actually ran and reproduced 
  results were obtained.

\aebench takes as input the artifact with its README 
  that lists installation, compilation, dataset preparation, 
  and experiment execution steps.
It also takes a set of four oracles for each the four 
  stages of running and reproducing results 
  ~\bo{I initially called this ``artifact evaluation stages'',

  how artifact evaluation is done as opposed to how 
  experiments in general are ran using software artifacts.
  So I need a better way to describe this early on}
Finally it takes a configuration file that specifies the 
  prompt along with execution parameters (where to execute 
  the artifact -- Docker vs. local machine, for how long, etc.)

One interesting question is how to determine the checks themselves 
  are correct.
Our framework relies on agent-human interaction to do so.
An agent extracts the set of requirements and steps from 
  the artifact's README.
Then uses a pre-defined template and evaluation APIs to 
  generate checkers in a particular shape.
Then humans (either the creators of the artifact 
  or the evaluators themselves) are asked to validate 
  those checkers and add ground truth results.


\subsection{Executing an Agent}

%% here we can start by explaining the lifecycle of an artifact
The key role of \aebench is to be a platform for running 
  and evaluating agents that attempt to reproduce 
  scientific results.
Thus, \aebench doesn't implement its own agent or 
  reasoning loop.
Instead, it delegates planning and tool usage to 
  off-the-shelf, external agents.
The framework controls the execution environment, provides task 
  instructions, sets execution budgets, and provides monitoring 
  during the agent run.
Once done, it also runs a series of checks to validate and evaluate 
  the agents work.
The agent decides what commands to run, how best to follow instructions, 
  what to execute and what to skip, and, most importantly, when it 
  reasons when to terminate, either it fully reproduce the artifact 
  and successfully executed the experiments, or some unsurmountable blocker 
  has occurred.

This setup allows us to investigate and measure different agents on 
  the same task.

Agents can terminate successfully, report success, 
  or generate expected-looking output files without 
  completing the reproduction~\cite{yang-blog26, wu-arxiv26, baek-ase26}.
We also observe similar behavior in our experiments.
Worse still, reproduction involves multiple 
  operations, and an agent may successfully complete 
  some without reaching (or even skipping) others.

Thus, to check for this, \aebench runs execution checkers 
  derived from the artifact's README (so, specific 
  to the artifact) and tracks agent execution trace 
  independent of the agent itself.

These evaluation oracles examine the resulting environment 
  and evaluate four reproduction phases: 
  environment setup (did the agent succesfully setup the 
  experimental environment as required by the artifact?), 
  artifact build (did the agent compiled/build the artifact 
  components successfully), dataset preparation (did the agent 
  successfully downloaded and setup the datasets need for the experiments), 
  and experiment execution (did the agent executed the experiments and 
  generated the expected outputs?).
This separation also makes partial progress more visible and 
  allows to compar different agents on how they preform on 
  different subtasks of the reproducibility life-cycle.

\end{enumerate}

\subsection{Configuration Management}

The configuration module is particularly important because it controls 
  application and artifact settings.
It determines which artifact is reproduced, what environment the agent receives,
  what instructions it sees, and which conditions determine its score.
The module also manages the configuration files associated with each artifact,
  including the runtime settings and the different oracle checks that are used 
    during evaluation.
These settings are not necessarily all specified in one place, because some are part 
  of the artifact definition and others depend on how \aebench is executed.
For example, the artifact configuration describes the different stages and requirements,
  whereas the execution settings also determine which agent and runtime backend are used.

The goal of \aebench is repeatability and reproducibility. So \aebench preserves
  some information about the execution and the configuration used for each run.
This is important also because two executions of the same artifact may not use exactly
  the same configuration, even if the artifact itself has not been modified.

First, the temporary workspace and permanent artifact-run output are different directories.
The workspace contains the files used by the agent during execution, while 
  the output directory stores information produced by the framework, 
  like logs and evaluation reports.
The workspace is also where the agent may modify source files, install software, or generate
  intermediate files during the reproduction procedure.
So when the workspace is removed, the report and logs should remain accessible 
  through the artifact-run output directory.

Second, retaining a failed workspace requires two settings to interact.
By default, that option is false, so workspaces are not explicitly cleaned 
  up at finalization.
This is also related to debugging, since keeping the workspace permits to inspect 
  what happened during a failed artifact reproduction.
In particular, the workspace may contain modifications made by the agent that are 
  not immediately visible from the final report, and therefore inspecting these 
  files can be useful.

Third, global default configurations do not uniformly override artifact settings.
  Some options are inherited from the global configuration while others are defined for
  each artifact separately.
The framework needs to resolve these settings before starting the execution,
  so that the runtime and the oracle evaluation use the corresponding values.
  For experimental runs, the effective configuration
  needs to be recorded after resolution, not inferred solely from environment variables.
This is necessary especially when comparing different agents, since differences in the
  configuration may influence the evaluation results.

\subsection{Framework orchestration}

\aebench orchestration module takes an artifact (\bo{should we say it's already verified and got three badges? probably this information should be in the evaluation section})
  and executes its reproduction experiment from beginning to end.
It coordinates the agent run, the runtime backend and the oracle checks.
The sequence matters because the oracles use the state left by the agent.
This module is responsible for the following workflow:
\begin{itemize}
  \item Preparation: Resolve the requested artifact and its configuration, obtain 
    the artifact source, create a workspace,
    generate the agent's prompt, and start its execution environment.
    The prompt tells the agent what it should reproduce.
    The workspace is where the agent runs commands and eventually modifies files.
  \item Agent execution: Launch the configured agent, enforce its time limit,
    and collect its execution result, including whether the agent terminated or timed out.
  \item State preservation: Stop the agent and, for configured Docker runs, save the
    resulting container filesystem so the oracles can inspect it.
    Some checks need the generated files, even if these files do not appear in the console output.
  \item Evaluation: Invoke the artifact-specific oracles against the
    resulting artifact and environment.
    The result of these checks is not necessarily the same as the exit status of the agent.
  \item Finalization: Combine the agent and oracle results, write the reports,
    and clean up temporary resources while keeping the run outputs.
\end{itemize}

\subsection{Oracle evaluation}

\aebench separates the agent execution from artifact evaluation.
The agent is given an artifact and asked to reproduce its results as documented
  by the authors in the paper and README.
Once the agent finishes, the oracle code independently inspects the resulting
  environment, files, executables, and experimental outputs.
For Docker runs, the checks may also need the saved container state,
  and not only the files that are visible in the workspace.
This is useful for tools installed inside the container that are not 
  present on the host machine.

The oracle subsystem answers four questions:

\begin{itemize}
  \item Did the agent prepare the required execution environment?
  \item Did it successfully build or install the artifact?
  \item Did it prepare the required benchmarks and experimental inputs?
  \item Did it execute the experiments and reproduce the expected results?
\end{itemize}

Each question corresponds to one evaluation phase. 
Each phase contains one or more checks.
A phase can contain several checks because, for example, there 
  may be multiple required tools or files.
For example, the build phase can check generated executables, and 
  experiment checks can inspect result files.

The main breakdown of this module is:

\begin{itemize}
  \item A phase is the unit of scoring.
  \item A check is the unit of verification inside a phase. Checks can test paths,
    run commands, or compare numeric results with reference values.
  \item An executor sub-module determines where the check runs: on the host, in the agent's resulting environment, or in a separate Docker image.
    The target is configured per phase, so different phases of an artifact may use different places.
  \item An oracle result aggregates the outcomes of the four phases into a score.
\end{itemize}

Importantly, the evaluation is artifact specific instead of just an e-dn-to-end generic 
  reproduction check.
\aebench provides a running framework, check primitives, and execution mechanisms.
Each artifact provides its own Python oracle defining what counts as successful reproduction.
The artifact also keeps reference data in \texttt{refs/}, such as expected numbers or lists of results,
  and the oracle chooses how much difference is acceptable for that particular experiment.

\subsection{Agent execution}

The agent execution module takes a artifact and a selected AI agent, then runs that agent as a 
  non-interactive process.

Specifically, it has five responsibilities:

\begin{enumerate}
  \item Construct the task presented to the agent.
  \item Prepare the credentials and environment needed by the selected agent.
  \item Launch agent with a model, permissions, and reasoning settings.
  \item Enforce an execution timeout and capture the agent's output.
  \item Return a compact process result to the orchestrator.
\end{enumerate}

The main design choice here is that \aebench delegates agent decisions to external coding agent CLIs. 
It does not implement its own LLM reasoning loop, tool-calling engine, or action planner. 
Thus, aqgents determine which commands to execute, which files to inspect, and 
  what changes to make.
Consequently, agent behavior depends on the particular version of the external agent CLI 
  and the underlying LLM model.

\subsection{Monitoring and reporting}

\aebench has modules responsible for recording agent activity, collecting command-level execution evidence,
  preserving experiment results, and visualizing the resulting trajectories.
The information is collected during the run and kept for inspection.

The relevant logic is divided into three parts:

\begin{itemize}
  \item Monitoring: capture commands executed through 
    instrumented shell, inside the agent environment.
  \item Reporting: produce structured results, logs, and reports, 
    with the agent and oracle outcomes.
  \item Trace visualization: converts recorded agent events into a 
    browsable execution history, so the steps can be inspected in order.
\end{itemize}

There is an important distinction between them.
Monitoring records what the agent does, reporting records the outcome of the run,
  and trace visualization reconstructs a view of the agent's execution.
None of these, by itself, decides whether the agent reproduced the artifact correctly.
The oracle remains responsible for that decision.

Similarly, the oracles are not responsible for validating that the agent actually
  executed the documented experiments that produced the results.
For that \aebench relies on two logs: the trajectory produced by the agent and
  the command list that \aebench runtime itself records.
These logs contain different views of the execution.
Then it uses an LLM-as-a-judge to compare the two, and then against the
  README of the artifact.


\subsection{Artifact results and instruction following checks}

\aebench checks two different things after the agent stops. 
First, whether the results satisfy the artifact-specific 
  oracles, without asking the agent if it succeeded. 
Second, whether the agent followed the README instructions. 

These two checks are related but not the same. 
An agent may generate the expected files after changing the benchmark 
  or using another workload. 
In both artifacts the numbers may look correct, although the procedure 
  was different. 
For example, it may edit a script to omit an expensive step and 
  still produce the expected output filename.

For artifact results, the oracle checks the environment, installed binaries, 
  benchmark inputs and output files, using checks and reference 
  values defined for that artifact. 
Checks go beyond file existence. 
Some may execute a command, or compare numbers with a stored 
  reference and tolerance. 
The four phases provide partial results, then the framework combines them 
  in a final score and report.

For instruction following, we compare the agent trajectory, 
  shell commands captured by instrumentation, and README steps. 
An LLM judge compares these sources to identify skipped steps, 
  extra commands, or changes not documented. 
The shell log contains only observed commands, so some agent operations 
  may be missing. It is not always possible to associate one 
  command with one output file. 
This check gives an indication, but is not an exact proof 
  of what generated a result.
